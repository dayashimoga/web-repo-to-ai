## 1. Executive Summary & Security Philosophy

`web-repo-to-ai` provides conversion of private GitHub repositories into AI-ready canonical context documents ([`CdmDocument`]). To perform conversion without compromising enterprise security or exposing developer credentials, the platform relies **exclusively on GitHub App authorization**.

```
+-----------------------------------------------------------------------------------------+
|                                    SECURITY COMPARISON                                  |
+--------------------------+------------------------------+-------------------------------+
| Mechanism                | Scope Granularity            | Credential Exposure Risk      |
+--------------------------+------------------------------+-------------------------------+
| Personal Access Token    | Broad account-wide access    | HIGH (Leaked token exposes    |
| (Classic / Fine-grained) | tied to individual user      | all user repositories)        |
+--------------------------+------------------------------+-------------------------------+
| OAuth App                | Broad user-delegated scopes  | MEDIUM (Cannot restrict       |
| (User Token)             | (`repo` gives write & admin) | to specific repositories)     |
+--------------------------+------------------------------+-------------------------------+
| GitHub App               | FINE-GRAINED least privilege | VERY LOW (Short-lived 1-hr    |
| (Installation Token)     | explicitly selected repos    | tokens, strictly read-only,   |
|                          | strictly read-only scopes    | tenant-isolated)              |
+--------------------------+------------------------------+-------------------------------+
```

### The Core Invariants of Rule 05

1. **Strictly Read-Only Access:** The application requests only `Contents: Read-only` and `Metadata: Read-only`. Write, commit, pull request creation, or administrative permissions are **strictly forbidden** and systematically rejected by runtime validation in [`web_repo_to_ai_github_extractor::GitHubAppPermissions`].
2. **Ephemeral Installation Tokens:** Repository extractions never use static keys. Instead, the backend generates a short-lived JSON Web Token (JWT) signed by an RSA private key, exchanges it for an installation access token valid for **at most 60 minutes**, and discards the token upon completion or expiry.
3. **Multi-Tenant & Installation Isolation:** Installation access tokens are scoped exclusively to the specific repositories selected by the organization administrator. Cross-tenant or cross-installation data access is cryptographically and architecturally prevented.
4. **Zero Credential Exposure:** Secrets (`client_secret`, `private_key_pem`, `webhook_secret`, and token strings `ghs_*`) are masked with `[REDACTED_SECRET]` across all `Debug`, `Display`, and logging implementations.

## 2. GitHub App Creation Methods

Operators and self-hosters can register their GitHub App using either an automated 1-click manifest flow or the manual GitHub web interface.

### Method A: Automated 1-Click Manifest Flow (Recommended)

GitHub supports registering Apps automatically from a JSON manifest payload. `web-repo-to-ai` provides a programmatic generator:

```rust
use web_repo_to_ai_github_extractor::GitHubAppManifestGenerator;

let generator = GitHubAppManifestGenerator::new("web-repo-to-ai-converter", "https://your-domain.example.com")
    .with_description("Universal URL & GitHub Repository -> AI-Ready Content Converter")
    .with_public(false);

let create_url = generator.to_manifest_create_url(None)?;
println!("Open this URL in your browser to create the app with 1 click:\n{}", create_url);
```

#### Manifest JSON Schema

When submitting to `POST /settings/apps/new?manifest={json}`, the payload generated by [`GitHubAppManifestGenerator`] conforms to:

```json
{
  "name": "web-repo-to-ai-converter",
  "url": "https://your-domain.example.com",
  "hook_attributes": {
    "url": "https://your-domain.example.com/api/v1/github/webhooks",
    "active": true
  },
  "redirect_url": "https://your-domain.example.com/api/v1/github/oauth/callback",
  "callback_urls": [
    "https://your-domain.example.com/api/v1/github/oauth/callback"
  ],
  "setup_url": "https://your-domain.example.com/settings/integrations/github",
  "description": "Universal URL & GitHub Repository -> AI-Ready Content Converter",
  "public": false,
  "default_permissions": {
    "contents": "read",
    "metadata": "read"
  },
  "default_events": [
    "installation",
    "installation_repositories"
  ]
}
```

### Method B: Manual GitHub Web UI Setup

To create the GitHub App manually via the GitHub web portal:

1. Log into GitHub and navigate to:
   - For Personal Accounts: **Settings > Developer Settings > GitHub Apps > New GitHub App**
   - For Organizations: **Organizations > [Your Org] > Settings > Developer Settings > GitHub Apps > New GitHub App**
2. **Basic Information:**
   - **GitHub App name:** `web-repo-to-ai` (or your company-specific name)
   - **Homepage URL:** `https://your-domain.example.com` (or `http://localhost:5173` for local development)
3. **Identifying and Authorizing Users (OAuth Flow):**
   - **Callback URL:** `https://your-domain.example.com/api/v1/github/oauth/callback`
   - **Request user authorization (OAuth) during installation:** Checked
4. **Post-Installation Setup:**
   - **Setup URL (optional):** `https://your-domain.example.com/settings/integrations/github`
   - **Redirect on update:** Checked
5. **Webhook Configuration:**
   - **Active:** Checked
   - **Webhook URL:** `https://your-domain.example.com/api/v1/github/webhooks`
   - **Webhook secret:** Generate a secure random 32-character hex string (e.g. `openssl rand -hex 20`). Save this for `GITHUB_APP_WEBHOOK_SECRET`.
6. **Repository Permissions (Strict Minimal Configuration):**
   - **Contents:** `Read-only` *(Allows reading source code, directory trees, blobs, commits, and tags)*
   - **Metadata:** `Read-only` *(Automatically required by GitHub; allows reading repository names, topics, default branch)*
   - **All other permissions:** Set to `No access`
7. **Subscribe to Events:**
   - Check `Installation` *(notifies backend when an installation is created or deleted)*
   - Check `Installation target` or `Installation repositories` *(notifies backend when repositories are added or removed)*
8. **Where can this GitHub App be installed?:**
   - **Only on this account** (recommended for private enterprise self-hosting)
   - **Any account** (for multi-tenant SaaS deployments)
9. Click **Create GitHub App**.
10. **Generate Private Key:**
    - On the newly created App's settings page, scroll down to **Private keys**.
    - Click **Generate a private key**.
    - A `.pem` file will download to your machine. Store this file securely; it is required for `GITHUB_APP_PRIVATE_KEY_PEM`.

## 3. Permissions & Events Reference Matrix

The following matrix documents the exact permissions evaluated by [`web_repo_to_ai_github_extractor::GitHubAppPermissions`]:

| Scope / Category | Permission Level | Rationale | Policy Status |
| :--- | :--- | :--- | :--- |
| **Repository: Contents** | `Read-only` | Required to read repository file trees, blobs, commits, tags, and archives. | **MANDATORY** |
| **Repository: Metadata** | `Read-only` | Required to query repository identification, stars, license, and branch names. | **MANDATORY** |
| **Repository: Administration** | `No access` | Modifying repository settings or access controls is forbidden. | **STRICTLY PROHIBITED** |
| **Repository: Actions** | `No access` | Interacting with CI/CD workflows is not required for context extraction. | **STRICTLY PROHIBITED** |
| **Repository: Pull Requests** | `No access` | Code conversion does not require commenting or approving PRs. | **STRICTLY PROHIBITED** |
| **Repository: Issues** | `No access` | Issue tracking is outside the scope of repository context conversion. | **STRICTLY PROHIBITED** |
| **Repository: Secrets** | `No access` | The engine never inspects repository secrets or environment variables. | **STRICTLY PROHIBITED** |
| **Organization: Members** | `No access` | User membership queries are not required. | **PROHIBITED** |

> [!CAUTION]
> If any administrator attempts to grant `Contents: Write` or any administrative permission, [`GitHubAppPermissions::validate`] will return an explicit error rejecting the configuration to preserve the integrity of Rule 05.

## 4. Webhook Events & Lifecycle Tracking

`web-repo-to-ai` listens for asynchronous webhook events on `/api/v1/github/webhooks` to keep the local database synchronized with installation state changes:

```
+-------------------+       Webhook Event POST        +-----------------------------+
|    GitHub.com     | ------------------------------> | services/api                |
|                   |   X-Hub-Signature-256: sha256=  | (crates/github-extractor)   |
+-------------------+                                 +-----------------------------+
                                                                     |
                                                       1. Verify HMAC-SHA256 signature
                                                       2. Parse event payload
                                                       3. Update installation records
                                                                     v
                                                      +-----------------------------+
                                                      | PostgreSQL (crates/storage) |
                                                      | - github_installations      |
                                                      | - github_installed_repos    |
                                                      +-----------------------------+
```

### Subscribed Events

1. **`installation`:**
   - `action: created`: Records the newly authorized `installation_id`, account details, and permissions in the database.
   - `action: deleted`: Marks the installation as revoked and soft-deletes stored tokens.
   - `action: suspend` / `unsuspend`: Temporarily pauses or restores access for the installation.
2. **`installation_repositories`:**
   - `action: added`: Updates the list of repositories accessible to the installation.
   - `action: removed`: Revokes local access to the removed repositories.

### Webhook Signature Verification Algorithm

Every incoming webhook request contains the `X-Hub-Signature-256` header formatted as `sha256=<hex_digest>`. The verification algorithm:

$$\text{Expected} = \text{HMAC-SHA256}(\text{key} = \text{webhook\_secret}, \text{data} = \text{request\_body})$$

Validation must use constant-time comparison ([`constant_time_eq`]) to prevent timing side-channel analysis:

```rust
use sha2::Sha256;
use hmac::{Hmac, Mac};

type HmacSha256 = Hmac<Sha256>;

pub fn verify_webhook_signature(secret: &[u8], body: &[u8], signature_header: &str) -> bool {
    let hex_sig = match signature_header.strip_prefix("sha256=") {
        Some(hex) => hex,
        None => return false,
    };
    
    let expected_bytes = match hex::decode(hex_sig) {
        Ok(b) => b,
        Err(_) => return false,
    };
    
    let mut mac = match HmacSha256::new_from_slice(secret) {
        Ok(m) => m,
        Err(_) => return false,
    };
    mac.update(body);
    
    mac.verify_slice(&expected_bytes).is_ok()
}
```

## 5. Cryptographic Keys & Token Lifecycle

Authentication with GitHub Apps operates on a two-tier token exchange protocol:

```
+-----------------------------------------------------------------------------------------+
|                                TOKEN EXCHANGE LIFECYCLE                                 |
+-----------------------------------------------------------------------------------------+
|                                                                                         |
|  1. Sign JWT (RFC 7519)                                                                 |
|     - Header: { "alg": "RS256", "typ": "JWT" }                                          |
|     - Claims: { "iss": APP_ID, "iat": now - 60s, "exp": now + 600s }                    |
|     - Key: RSA Private Key (.pem)                                                       |
|                                                                                         |
|  2. Authenticate as App                                                                 |
|     GET https://api.github.com/app                                                      |
|     Authorization: Bearer <JWT>                                                         |
|                                                                                         |
|  3. Request Installation Access Token                                                   |
|     POST https://api.github.com/app/installations/{installation_id}/access_tokens       |
|     Authorization: Bearer <JWT>                                                         |
|     Response: { "token": "ghs_...", "expires_at": "2026-11-18T12:30:00Z" }              |
|                                                                                         |
|  4. Extract Private Repository                                                          |
|     GET https://api.github.com/repos/{owner}/{repo}/git/trees/{commit_sha}?recursive=1  |
|     Authorization: Bearer ghs_...                                                       |
|     (Token valid for 60 minutes max; cached with 5-minute safety expiration margin)     |
+-----------------------------------------------------------------------------------------+
```

### Private Key Specifications

The GitHub App RSA private key must meet the following cryptographic requirements:
- **Algorithm:** RSA 2048-bit or 4096-bit key pair.
- **Encodings Supported:**
  - **PKCS#1:** Header `-----BEGIN RSA PRIVATE KEY-----` and footer `-----END RSA PRIVATE KEY-----`.
  - **PKCS#8:** Header `-----BEGIN PRIVATE KEY-----` and footer `-----END PRIVATE KEY-----`.
- **Validation:** [`web_repo_to_ai_github_extractor::GitHubAppConfig::validate`] verifies these delimiters upon loading.

## 7. Operational Troubleshooting & Runbook

### Issue: "Invalid private key PEM format"
- **Cause:** The private key string does not contain valid PEM delimiters or has suffered line break mangling in environment variable injection.
- **Remediation:** If passing via Docker/Podman `.env`, wrap the PEM string in quotes with `\n` characters or mount the file as `/secrets/github-app-key.pem` and provide the file path in `GITHUB_APP_PRIVATE_KEY_PEM`.

### Issue: "GitHub API HTTP 401 Unauthorized"
- **Cause:** Clock skew between the host machine and GitHub's servers, causing the JWT `iat` (issued at) claim to appear in the future.
- **Remediation:** `web-repo-to-ai` automatically subtracts 60 seconds from `iat` to tolerate minor clock skew. Ensure host system NTP synchronization is active.

### Issue: "GitHub API HTTP 404 Not Found on Private Repo"
- **Cause:** The GitHub App is installed on the organization, but the specific target repository was not selected during installation, or the installation token was not provided.
- **Remediation:** Direct the user to their GitHub App installation settings (`https://github.com/settings/installations/{installation_id}`) and verify that the target repository is included under **Repository access**.

### Issue: "Secondary Rate Limit / 403 Forbidden"
- **Cause:** Too many concurrent requests hitting GitHub REST API from a single installation.
- **Remediation:** GitHub Apps receive 5,000 requests per hour per installation (up to 15,000 req/hr for GitHub Enterprise). Ensure bounded concurrency semaphore in [`web_repo_to_ai_github_extractor::client::GitHubApiClient`] is observed.
